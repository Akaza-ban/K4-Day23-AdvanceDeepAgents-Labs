# LLM Agents and Tool Use: A Survey of Foundations, Architectures, Evaluation, and Safety

## TL;DR

- **Tool use is the standard remedy for the intrinsic deficits of frozen language models.** The founding papers enumerate the same list of pathologies — stale knowledge, factual hallucination, imprecise arithmetic, weak low-resource-language handling, and no sense of elapsed time — and answer them with external modules: a calculator, a QA engine, a search engine, a translator, and a calendar [1], a neuro-symbolic router over discrete "experts" [2], or a browser environment trained with human feedback [3]. The resulting control pattern, ReAct's interleaving of *Thought → Action → Observation* [4] on top of chain-of-thought prompting [5], remains the canonical agent loop.
- **The method space has consolidated into four families — prompting, self-supervised/SFT distillation, retrieval-augmented tool selection, and reinforcement/preference optimization on trajectories — and they compose.** Toolformer keeps self-generated API calls only when they reduce next-token loss [1]; ToolLLM distills ChatGPT solution paths over 16,464 real RESTful APIs into ToolLLaMA with a neural API retriever [6][7]; RL on tool trajectories (ToolRL, Tool-Zero, Agent-R) is the fastest-moving frontier and is argued to generalise better to unseen tools than SFT [8][9][10]. Execution feedback and code-as-action unify the loop: CodeAct makes Python the action space [11], and MCP standardises tool discovery/invocation across hosts and servers [12][13].
- **Empirically, frontier agents still fail most realistic tool-use tasks, and reliability decays sharply with horizon.** Best GPT-4 agents reach 14.41% end-to-end success on WebArena versus 78.24% for humans [14]; GPT-4 with plugins reaches 15% on GAIA versus 92% for humans [15]; τ-bench's `pass^8` for gpt-4o collapses below 25% on τ-retail even though `pass^1` is ~61% [16]. The closed-vs-open gap is large but narrowing: API-based models averaged 2.32 versus 0.51 for open-weight models on AgentBench's original 29-model study [17].
- **Retrieval of tools is not the bottleneck; selection, argument correctness, and recovery are.** ToolLLaMA with a neural API retriever has been reported to match or slightly *beat* oracle-API prompting on average pass rate (reported as 67.3% vs 66.7%; a leaderboard-snapshot figure that should be treated as indicative) [6][7], yet MetaTool shows most LLMs struggle simply to decide whether a tool is needed and which one to pick [18], and error taxonomies converge on wrong tool choice, parameter hallucination, rule-following failures, and `Task Limit Exceeded` long-horizon collapse [16][17].
- **Safety is now the gating problem, and the consensus is that defenses must be architectural rather than interceptive.** Because prompts carry no instruction/data boundary, indirect prompt injection via retrieved content or tool output is treated as intrinsic [19][20]; measured attack success rates are high (InjecAgent: 24% on ReAct-prompted GPT-4 [21]; CyberSecEval 2: 26–41% [22]; Agent-SafetyBench: no agent above 60% safety on 2,000 cases [23]), and MCP adds protocol-level surfaces — tool poisoning, "line jumping", rug pulls, and cross-server trust propagation [24][25][26]. Containment (sandboxing, credential isolation, least privilege, step-level guardrails) outperforms instruction-level defenses [27][28][29][30].

## Background

**Why tools at all.** The motivation for tool-augmented language models is stated most explicitly by Toolformer, which lists an inability to access up-to-date information, a tendency to hallucinate facts, difficulties with low-resource languages, a lack of mathematical skill for precise calculation, and an unawareness of the progression of time, and then attaches a calculator, a question-answering system, a search engine, a translation system, and a calendar to a 6.7B GPT-J model [1]. Gorilla frames the same gap in deployment terms: language models are bounded by what they can store in a fixed set of weights, so as "the world changes, LLMs require retraining to update their knowledge" — while cloud APIs themselves change frequently [31]. MRKL argues that language models are inherently limited and proposes a modular neuro-symbolic system in which an extendable set of discrete "experts" is addressed by a router, implemented as Jurassic-X [2]. WebGPT pre-dates most of this literature by training GPT-3 to answer long-form questions inside a text-based browsing environment using the Bing Web Search API, with imitation learning plus human-feedback rejection sampling; its answers were preferred 56% of the time over human demonstrators and 69% over the top Reddit answer on ELI5 [3]. The Augmented Language Model survey generalises the framing, organising the field along reasoning augmentation and tool use/acting, and distinguishing heuristic from learned (supervised or RL) augmentation [32]; later surveys unify tool use (including RAG), planning, and feedback learning under shared role abstraction [33] and offer a unified definition of tools as external programs used by LMs [34].

**The canonical loop.** Chain-of-thought prompting established the reasoning substrate: few-shot exemplars containing input, chain of thought, and output elicit multi-step reasoning, with gains that emerge only around 100B parameters and 8 exemplars that let PaLM 540B reach state of the art on GSM8K [5]. ReAct then interleaves verbal reasoning traces with task-specific actions and observations in a single model pass, letting reasoning induce and update action plans while actions gather information from external sources such as a Wikipedia API; one- or two-shot ReAct prompting beat imitation and RL baselines trained on 10^3–10^5 instances, with +34% and +10% absolute success-rate gains on ALFWorld and WebShop respectively — and it framed acting as a way to reduce the hallucination and error propagation of pure chain-of-thought [4]. Task taxonomies describe the same pipeline as instruction understanding, subtask decomposition, plan adjustment through reasoning, and per-subtask tool selection over a controller/tool-set/environment/perceiver/human framework [35][36], while agent surveys decompose agents into profile, memory, planning, and action modules [37] or into brain, perception, and action [38], and a 2025 methodology-centred survey notes that tool use decomposes into a tool-use decision and a tool-selection problem [39].

**Formalisation as sequential decision making.** The agentic-RL survey draws the sharpest formal contrast: preference-based fine-tuning of a language model is a "degenerate single-step MDP" whose state is one prompt and whose episode ends immediately, whereas agentic RL is a partially observable, temporally extended POMDP `⟨S_agent, A_agent, P_agent, R_agent, γ, O⟩` with observation `o_t = O(s_t)`, action space `A_text ∪ A_action`, and step-wise rewards; it places tool use among the RL-optimisable capabilities alongside planning, memory, self-improvement, reasoning, and perception, and describes the shift from post-hoc ReAct-style pipelines to multi-turn tool-integrated reasoning [40]. Earlier paradigm reviews likewise note works that transform NLP tasks into Markov decision processes for deliberate multi-step workflows, distinguishing passive RAG-style tool use from autonomous tool use triggered during generation, by reasoning-acting, or by confidence [33].

**Founding systems and benchmarks.** The field's initial landmarks can be dated precisely: WebGPT (2021-12-17) [3], MRKL (2022-05-02) [2], ReAct (2022-10-06) [4], Toolformer (2023-02-09) [1], HuggingGPT (2023-03-30), which runs a four-stage controller loop of task planning, model selection, task execution, and response generation over Hugging Face expert models [41], API-Bank (2023-04-14) [42], Tool Learning with Foundation Models (2023-04-17) [35], Gorilla (2023-05-25) [31], ToolLLM/ToolBench (2023-07-31), with 16,464 RESTful APIs across 49 RapidAPI categories, depth-first search decision tree annotation, ToolLLaMA, and the ToolEval evaluator [6], MetaGPT (2023-08-03), whose SOP-driven multi-agent "software company" gains +5.4% absolute on MBPP from executable feedback [43], and the MetaTool benchmark (2023-10-04) [18].

## Theme 1 (Comparative Analysis): Architectures and Learning Methods for Tool Use

The literature partitions cleanly into prompting-only, self-supervised/SFT distillation, retrieval-augmented selection, and RL/preference optimisation, with execution feedback and orchestration as a systems layer above them.

**Prompting-only orchestration** requires no weight updates. ReAct's thought/action/observation loop is the template [4]; Tree-of-Thoughts generalises chain-of-thought into explicit search with generation, self-evaluation, lookahead, and backtracking, lifting GPT-4's Game-of-24 accuracy from 4% (CoT) to 74% [44], and thus supplies the pattern for search over candidate tool calls; Reflexion reinforces agents linguistically rather than by gradient updates, storing verbal self-reflections in an episodic buffer to guide subsequent attempts [45]; Reverse-Chain-style target-driven prompting plans multi-API workflows by completing API arguments before execution [36]. A controlled critique, however, shows that ReAct's apparent sequential-decision-making advantage is largely attributable to similarity between in-context examples and the query, i.e. "brittle foundations" [46] — a caution that the loop's benefit cannot be assumed to be genuine reasoning.

**Self-supervised synthesis and SFT distillation** remove the human annotation bottleneck. Toolformer samples candidate API calls over a pretraining corpus and retains only those that reduce the loss on subsequent tokens before fine-tuning [1]. ToolLLM scales the idea into a dataset: instructions are generated by ChatGPT for single- and multi-tool scenarios over 16,464 real APIs in 49 categories, solution paths are annotated by a depth-first search decision tree (DFSDT) that lets the model expand and evaluate alternative traces, and the filtered traces fine-tune LLaMA into ToolLLaMA [6]. Gorilla fine-tunes a LLaMA-7B with a document retriever attached at inference so the model adapts to test-time documentation changes; it reports writing API calls 20.43% more accurately than GPT-4 zero-shot [31]. TRICE adds a two-stage recipe that learns from execution feedback rather than depending solely on a strong teacher [47], DRAFT refines tool documentation from interaction data [36], and ToolAlpaca shows that 3,000 simulated cases suffice to bring compact models close to large-model tool-use ability [48]. A 2025 survey argues small (1–12B, up to ~20B) language models are often sufficient for agentic workloads whose accuracy is schema-constrained, pairing them with guided decoding stacks [49].

**Retrieval-augmented tool selection** is unavoidable at realistic tool counts, since top-k filtering is needed given context-length and latency limits [36]. Retrieval quality is actively engineered: synthetic tool descriptions align user queries with tools (ToolDreamer) [50], LLM↔retriever iterative feedback improves cross-domain retrieval [51], and small encoders plus synthetic data make tool representations cheap enough to scale (Tool2Vec-style methods) [52]. Preference optimisation has been extended from models to retrievers by PORTS-style odds-ratio objectives [6][50].

**RL and preference optimisation on tool trajectories** is the most active frontier. ToolRL argues SFT generalises poorly and that a principled RL reward (with GRPO) yields 17% improvement over base models and 15% over SFT models with strong generalisation to unseen scenarios, while warning that higher training rewards do not necessarily imply better generalisation [8]. Tool-Zero trains from base models with no SFT at all using a dynamic generalisation-guided reward, reporting a gain over ToolACE-8B, and documents the SFT pathology directly: SFT lifts in-distribution "Live" performance substantially while giving negligible or negative gains on Non-Live and Multi-Turn subsets [9]. GenTool frames generalisation as zero-to-one and weak-to-strong and reports that existing LLMs rely heavily on memorising tools rather than understanding their use [53]. Agent-R uses Monte-Carlo-tree-search-driven iterative self-training so agents learn to reflect and correct actions mid-trajectory [10]; DMPO adapts direct preference optimisation to multi-turn agent tasks by normalising trajectory lengths in the objective [54]; and the underlying DPO reparameterisation of the RLHF reward into a simple classification loss underpins much of this line [54]. The mechanism-level comparison is thus: prompting is free but brittle [46]; SFT is cheap but overfits tool identity [8][9]; RL generalises better at the cost of reward engineering and reward-hacking risk [8][53].

**Execution feedback and code-as-action** couple acting to verification. ReAct's observation loop [4] and Reflexion's verbal feedback [45] are the parents; Self-Debugging teaches models to explain their own predicted programs in natural language ("rubber-duck debugging") without human feedback [55]; self-repair studies find GPT-4 repairs beat GPT-3.5 and improve further when the feedback comes from GPT-4 or human programmers [55]. CodeAct goes furthest, unifying the action space as executable Python so that agents can self-debug and dynamically revise actions across turns [11]. Reviews frame this as a shift from heuristics to learned feedback loops [33].

**Multi-agent and protocol-level orchestration** is where research meets deployment. ConAgents modularises the tool-learning workflow across cooperative agents with feedback calibration [56]; MetaGPT encodes standard operating procedures across roles with executable feedback [43]; HuggingGPT uses ChatGPT as controller over expert models [41]. In industry runtimes, LangGraph models workflows as state graphs with a prebuilt tool node that executes tools in parallel with error handling, and documents orchestrator-worker, routing, and evaluator-optimiser patterns [57]. Above the framework layer, the Model Context Protocol, introduced by Anthropic in November 2024, replaces N×M integrations with a single host/client/server protocol built on JSON-RPC 2.0, exposing tools, resources, and prompts, with discovery via `tools/list` and execution via `tools/call` [13][12][58]. Long-horizon memory is the emerging enabler: hierarchical memory and SOP compression for context density, RL over context-editing actions, and systems-level characterisation of how memory design distributes cost between storage and retrieval [39].

## Theme 2 (Comparative Analysis): Evaluation and Empirical Performance

**The benchmark stack.** Tool-use evaluation has converged on execution-grounded metrics. API-Bank provides 73 runnable API tools, 314 annotated tool-use dialogues with 753 API calls, and a training set of 1,888 dialogues drawn from 2,138 APIs across 1,000 domains; its Lynx model (built from Alpaca) beats Alpaca's tool utilisation by more than 26 points and approaches GPT-3.5 [42]. ToolBench pairs 16,464 real APIs with ToolEval, whose pass rate measures completion within a limited API budget and whose win rate is a pairwise preference against a reference solution, validated at 87.1% and 80.3% agreement with human annotators [6][7]. APIBench/Gorilla pioneered API-call accuracy testing over TorchHub, TensorHub, and Hugging Face APIs [31]. The Berkeley Function Calling Leaderboard introduced AST-based and executable checking over roughly 2k question-function-answer pairs spanning Python, Java, JavaScript, REST API, and SQL, later adding "live" enterprise-contributed data, relevance detection, multi-turn/multi-step evaluation, and finally holistic agentic evaluation with cost and latency reporting [59][60][61]. τ-bench evaluates an agent with domain API tools and policy guidelines conversing with a simulated user, scoring the final database state against an annotated goal and introducing `pass^k` for consistency [16]. WebArena supplies self-hosted functional websites for long-horizon tasks scored by functional correctness [14]; GAIA contributes 466 real-world questions requiring browsing and multimodal tool use, designed so answers are absent from pretraining text and 300 questions are withheld for a leaderboard [15]; AgentBench spans eight environments from OS, database, and knowledge graph to games and web shopping, with 269/1,014 dev/test instances [17]; SWE-bench contributes 2,294 real GitHub issue-resolution tasks scored by `% Resolved` [62]; MINT evaluates multi-turn interaction with tools and natural-language feedback [63]; AgentBoard adds a fine-grained progress-rate metric to complement binary success [64]; and MetaTool isolates tool-usage awareness and tool selection across four selection subtasks for eight LLMs [18].

**How good are agents, really?** The consistent answer is: not good. GAIA reports 92% for human respondents against 15% for GPT-4 with plugins, with GPT-4 at or below 30% on the easiest tier and 0% on the hardest [15]. WebArena's best GPT-4 agent achieves 14.41% end-to-end success versus 78.24% for humans [14]. On τ-bench, gpt-4o function calling reaches roughly 61% `pass^1` on τ-retail while the `Act` baseline of the same model reaches roughly 36% on τ-airline — the per-domain tool-calling strategy is the harder setting [16]. On AgentBench's 29-model study, gpt-4 led six of eight environments and reached 78% on House Holding, but API-based models averaged 2.32 overall versus 0.51 for open-source models, with the best open model at ≤70B (codellama-34b) at 0.96 — the authors concluded gpt-4 was "not qualified as a practically usable agent" [17]. On ToolBench, ChatGPT+DFSDT reached 64.8 average pass and 64.3 win, GPT-4+DFSDT 71.1/70.4, and ToolLLaMA+DFSDT 66.7/60.0; against that, Claude-2+ReAct averaged 6.8 pass and Vicuna and Alpaca reached zero [6][7]. A striking architectural result is that ChatGPT+DFSDT (64.8) surpassed GPT-4+ReAct (57.2) on pass rate [7], i.e. the search strategy can matter as much as the base model.

**Retrieval is not the bottleneck.** On ToolBench, ToolLLaMA equipped with a non-oracle neural API retriever has been reported to match or slightly exceed its oracle-API configuration on average pass rate (reported as 67.3% versus 66.7%; treat these leaderboard-snapshot figures as indicative rather than definitive, since independent retrieval of the leaderboard table was not possible) [6][7] — retrieving a candidate set did not degrade and may have helped by widening the candidate space. The harder problems are deciding *whether* a tool is required and *which* to use [18], and getting arguments right.

**Reliability, not just mean success.** τ-bench's `pass^k` — the probability that all k trials succeed — exposes horizon fragility: gpt-4o falls from roughly 61% `pass^1` to below 25% `pass^8` on τ-retail, and the benchmark's authors note that even state-of-the-art function-calling agents succeed on fewer than half of tasks and are "quite inconsistent" [16]. Cost is non-trivial: roughly $0.38 for the agent plus $0.23 for the user simulator per τ-retail task, about $200 for one trial across the set [16].

**Error modes and failure attribution.** Documented failure classes are wrong or unnecessary tool selection (MetaTool; BFCL relevance detection) [18][59], parameter errors (τ-bench counts tool calls with non-existent IDs as a proxy; gpt-3.5-turbo function calling made 2.08 such calls per τ-retail task versus 0.46 for gpt-4o function calling) [16], policy/rule-following failures (removing the policy system prompt degraded gpt-3.5-turbo by 4.4–5.5% on τ-retail and caused a large drop on the rule-heavy τ-airline domain) [16], and long-horizon degradation — AgentBench's dominant failure cause is `Task Limit Exceeded`, i.e. weak long-term reasoning and instruction following [17]. Encouragingly, feedback helps: MINT finds tool use adds 1–8% per turn and natural-language feedback 2–17%, while noting that better single-turn performance does not imply better multi-turn performance and that SIFT and RLHF training "generally hurt" multi-turn capability [63]. Dedicated stress tests now probe recovery explicitly, including tool-environment unreliability [65] and self-critique in tool-calling error scenarios [66], and long-horizon planning in large tool ecosystems with dynamic disruptions [67].

**Contamination and reproducibility are first-order concerns.** StableToolBench found that only 44.4% of real ToolBench API calls succeeded — expired APIs, network failures, authentication problems and schema changes caused high variance and an observed decline in all methods over time — motivating a virtual API server with caching and simulation plus a stable evaluator over solvable tasks (SoPR/SoWR) [68][7]. On coding agents, SWE-Bench+ found 32.67% of "successful" patches contained solution leakage and 31.08% passed weak tests; after filtering, SWE-Agent+GPT-4's resolution rate fell from 12.47% to 3.97%, and to 0.55% on a de-contaminated benchmark [69]. Contamination surveys classify detection into matching-based and comparison-based methods and mitigation into data curation, refactoring, and benchmark-free evaluation, citing evidence that prompt variation alone can cut measured performance by an average of 39.4% across 51 models [70]; static-to-dynamic benchmarking surveys note that dynamic benchmarks reduce contamination but lack standardised criteria and trade off reproducibility and compute [71]. A 2025 survey of agent evaluation identifies limited task coverage, fragmented metrics, high reproduction costs, and misalignment with human values as the principal gaps [72]. Cross-version and cross-snapshot comparisons must therefore be treated as non-comparable [60][61].

## Theme 3 (Comparative Analysis): Safety, Risks, and Open Problems

**The threat model is structural.** Language models place instructions and data in the same token stream, so no reliable boundary exists between them; OWASP defines prompt injection as inputs altering model behaviour in unintended ways and notes that RAG and fine-tuning do not fully mitigate it, with impact ranging from sensitive-information disclosure to arbitrary command execution in connected systems [20]. The 2026 OWASP list names prompt injection the clearest case and identifies three aggravating properties of agentic deployments: context-window pooling (no trust boundary between system prompt, user input, retrieved documents, tool outputs, and memory), memory persistence (an injection that writes to memory taints future sessions), and agentic execution (tool calls to file systems, shells, email, cloud APIs, and MCP servers extend blast radius) [73]. Greshake et al. systematised indirect prompt injection, showing that adversarially poisoned retrieved content acts as "arbitrary code" and that practical attacks against Bing Chat and code-completion engines can manipulate API calls, exfiltrate data, and deny service, with no effective mitigations available [19]; theoretical work cited there suggests defending against all undesired behaviour by alignment or RLHF is not possible, and defensive RLHF follows a "Whack-A-Mole" pattern [19].

**Quantified vulnerability.** InjecAgent provides 1,054 cases with 17 user tools and 62 attacker tools, split into direct-harm and private-data-exfiltration attacks; ReAct-prompted GPT-4 was compromised 24% of the time, rising with a reinforcing "hacking prompt" [21]. AgentDojo builds 97 realistic tasks (email, e-banking, travel) with 629 security test cases and finds agents fail many tasks even without attacks [74]. Agent-SafetyBench evaluates 16 agents over 349 environments and 2,000 test cases across eight risk categories and ten failure modes, and reports that **no agent exceeded 60%** safety, attributing this to insufficient robustness and risk awareness and finding defense prompts alone insufficient [23]. CyberSecEval 2 adds "code interpreter abuse" as a test area and finds 26–41% successful prompt injection across GPT-4, Mistral, Llama 3 70B-Instruct and Code Llama, formalising the safety–utility trade-off through a false refusal rate [22].

**Protocol-level surfaces.** The Model Context Protocol, designed to standardise tool integration [13][12], introduces attack classes that execute *before* any tool is invoked. Invariant Labs disclosed tool poisoning in April 2025: malicious instructions hidden in tool descriptions are invisible to users but visible to models, causing agents to read sensitive files such as `~/.cursor/mcp.json` or `~/.ssh/id_rsa` and exfiltrate them while hiding the activity; the same architecture enables rug pulls (a server changes descriptions after approval) and tool shadowing (a malicious server alters behaviour with respect to a trusted one, enabling credential hijacking) [24]. Trail of Bits independently described "line jumping" — malicious servers manipulating model behaviour during `tools/list`, bypassing invocation-control and connection-isolation guarantees — and demonstrated it against Claude Desktop with payloads such as prefixing shell commands with `chmod -R 0666 ~;` [25]. A STRIDE+DREAD threat model across six MCP components identified 57 threats, scored tool poisoning Critical (46.5/50), and found that five of seven tested clients performed no static metadata validation; in the associated evaluation, malicious servers were uploaded to public aggregators with zero resistance and one was even labelled "safe to use" [26]. NIST AI 100-2e2025 supplies the corresponding taxonomy, covering prompt injection, indirect prompt injection, poisoning, prompt extraction, "compromising connected resources," and misaligned outputs organised by attacker goals and capabilities, including a dedicated section on agent security [75].

**Reliability and engineering constraints.** Beyond security, agents exhibit cascading error propagation in long-horizon settings, where a single early mistake corrupts state so that later actions appear wrong only because of their dependencies [74]. Calibrating when to stop and ask for help is explicitly framed as unsolved: too much checking in destroys autonomy, too little risks misreading intent, and models trained to pause show roughly double the check-in rate on complex versus simple tasks [76]. Step-level unsafe invocation is being attacked directly: ToolSafe builds a multi-task-RL guardrail that detects unsafe invocation before execution, reducing harmful tool invocations in ReAct-style agents by 65% on average while improving benign completion by about 10% under prompt injection [29]. Separately, agents frequently select higher-privilege tools than necessary, and safety alignment does not confer least-privilege behaviour — though post-training defenses can reduce excessive privilege use without losing performance [30]. Operationally, unbounded consumption is a named risk class [20][73], and decoupling the model-and-harness "brain" from sandboxed "hands" and an externalised append-only session log both improved latency (p50 time-to-first-token down roughly 60%) and gave context externalisation, slicing, and rewinding for context engineering [77].

**Defenses and their limits.** Recommended controls converge on layered containment: structured outputs with enums and fixed schemas so no freeform channel exists for smuggling instructions, routing untrusted content through user rather than developer messages, and per-operation tool approvals [28]; deterministic validation of expected output formats [20]; step-level guardrail models [29]; least-privilege execution and code-side handling of sensitive functions instead of granting the model API tokens [20]; human-in-the-loop approval with the caveat that approval degrades into fatigue — telemetry showed roughly 93% of permission prompts were approved, prompting a shift from per-step to per-plan oversight, while an OS-level sandbox (Seatbelt on macOS, bubblewrap on Linux) with default-deny network and workspace-only writes cut permission prompts by 84% [27]; VM-level isolation with credentials held in the host keychain so they never enter the guest [27][77]; and protocol hardening via tool and package pinning, hash checks, trust-on-first-use alerts on changed descriptions, and cryptographic signing [24][25][26]. Verifiably safe tool use has been approached with STPA-style hazard analysis and formal methods [26][78]. The limits are documented as well: adaptive attacks break static prompt-injection defenses [78], input-classification "AI firewalling" degrades because detecting a malicious input is as hard as detecting a lie [28], detector rankings on public benchmarks do not transfer to in-agent settings [78], and static benchmarks systematically underestimate vulnerabilities by ignoring malicious prompt optimisation and user underspecification [78][79].

## Trends and open problems

**Generalisation to unseen tools is the central unresolved learning question.** The 2024–2025 debate is whether RL-trained agents transfer better than SFT ones. ToolRL reports 17% improvement over base models and 15% over SFT models with strong generalisation to unseen scenarios, while cautioning that higher training rewards do not imply better generalisation [8]; Tool-Zero shows pure RL from scratch with a generalisation-guided reward beating both SFT and RL-with-SFT, and documents that SFT's in-distribution gains evaporate off-distribution [9]; GenTool concludes existing LLMs rely heavily on memorising tools rather than understanding their use, and formalises zero-to-one and weak-to-strong generalisation [53]. Reward design, reward hacking, and the right notion of tool-agnostic reward remain open [8][53].

**Scaffolds versus base-model capability.** Harnesses encode assumptions about what a model cannot do on its own, and those assumptions go stale as models improve, motivating general "meta-harness" interfaces rather than brittle hand-built pipelines [77]. Because behaviour depends on all four of model, harness, tools, and environment, a well-trained model can still be exploited through a permissive tool or an exposed environment [76] — which reframes capability evaluation as a system-level property and pushes evaluation toward large-scale tool ecosystems with dynamic disruptions [67].

**Reliability across horizon, and calibration of autonomy.** `pass^k` decay [16] and `Task Limit Exceeded` dominance [17] quantify a phenomenon that memory and context-management research tries to fix; step-attribution methods now treat multi-agent failure as a dependency-tracing problem rather than independent per-step classification [78][77], and knowing when to pause and ask remains explicitly unsolved [76]. Related open questions include non-determinism and reproducibility of agent runs, and the observability blind spot where a successful exfiltration is logged as an ordinary authorised API call [77].

**Evaluation credibility.** Contamination, leakage, and API instability are not peripheral: 44.4% real-API success on ToolBench [68], 32.67% solution leakage plus 31.08% weak tests and a collapse from 12.47% to 0.55% resolved on de-contaminated SWE-bench+ [69], and measured drops of ~39.4% under simple prompt variation [70]. Agent benchmarks additionally suffer limited task coverage, fragmented metrics, and high reproduction cost [72], while dynamic benchmarking trades contamination resistance for reproducibility and compute [71]. The field lacks standardised criteria for what makes an agentic benchmark valid [71][72].

**Security as an architectural discipline.** The most recent debate has moved past "does injection work" toward "which layer contains it". OWASP, NIST, and major labs converge on the position that no fool-proof interception exists and that defense must be architectural [20][73][75]. Open problems include agent identity and capability attestation (servers currently self-assert permissions, and multi-server contexts conflate outputs without provenance), cross-server dataflow control, and oversight that survives approval fatigue [27][26][76]. Empirical evidence that defense evaluations do not transfer — replayed ground-truth tool calls destroying detector rankings [78] and static suites underestimating adaptive attacks [79] — suggests that safety benchmarking must itself become dynamic and adaptive, mirroring the shift already underway in capability benchmarking [74][71].
